# FIX-001 — A manual run finishes the job, and can be stopped

**Built and verified on the Fold 4, 26 Aug 2026. Commit `5c124ac`.**

| Acceptance | Result |
|---|---|
| One press clears the backlog across many byte-budget runs | **yes** — six batches, 24 files, no intervention |
| Stop is offered while a chain is live and cancels the chain | **yes** — cancelled mid-file |
| A stopped file resumes from its offset, not byte zero | **yes** — resumed at 2%, then 14%, climbing across restarts |
| A manual chain is never held by the first-backup window | **yes** — `KEY_MANUAL` carried into every continuation |
| A cleared backlog lifts the gate | **yes** — `backlog cleared; first-backup window no longer applies`, and `first_backup_completed` written for the first time on this device |
| The screen never reports Finished with files remaining and no reason | **yes** — the worker publishes its outcome and the UI maps it |
| Stop reachable in the app, never only from a notification | **yes** — WorkManager path, no foreground service |

**One acceptance line remains unobserved:** the gate lifting *while it is holding* — the case where
someone clears everything manually during the day and automatic runs would otherwise keep insisting
they owe a first backup. The code is in and reached before the hold's early return, but the gate is
now permanently down on this device, so it cannot hold again without clearing app data. Worth
exercising on the next fresh install rather than manufacturing it here.

**Found while verifying, and fixed in the same commit:** the UI kept the last status it saw when work
finished, so a run that stopped on a full drive left "Uploading 2 of 16" on screen while the one
actionable fact was invisible. The worker now returns its counts and stop reason in `outputData`.

Milestone: v0.2.x — backup engine
Reported by: Ian, 26 Aug 2026, on the Fold 4 test rig
Found by: watching Haku upload 4 of 19 files and halt

## What Ian decided

> *"Any manually started operations should continue until completed or stopped by User — can we
> change the Sync Now button (once pressed) to a Stop Sync button? The 1 am setting was ONLY for the
> onetime initial backup — once all files are backed up, every backup/sync should happen until job
> is completed."*

Three rules, in order of how much needs building:

1. **A manual run runs to completion.** It ends when there is nothing left, when something genuinely
   stops it, or when the user says stop. Not when a byte budget trims the batch.
2. **The button is a toggle.** Pressing it starts the run; while running it offers Stop.
3. **The overnight window is only ever about the first backup.** Already true in design — see below.

## What was observed

Haku, 19 files, 1,107 MB, on a new empty account. One press of Sync now uploaded 4 files (499 MB)
and stopped. Nothing scheduled anything further. The screen said `Finished`, `stoppedBecause = null`,
15 remaining.

```
11:22:03  byte budget trimmed 19 candidates to 4
11:23:54  upload: stored 2025-03-03-082546535.mp4 (104914526 bytes)
          (nothing further)
```

No `backup run finished` line, because the worker never ran.

## Root cause — two engine hosts, one of which does no bookkeeping

`BackupWorker` and `BackupViewModel.runBackupNow` both drive `BackupEngine`, and everything the
worker does *around* the run is missing from the manual path.

| After a run | `BackupWorker` | `runBackupNow` |
|---|---|---|
| Logs the outcome | yes | no |
| Schedules the next batch when `remaining > 0` | yes, line 114 | **no** |
| Lifts the first-backup gate on `isComplete` | yes, line 106 | **no** |

`runBackupNow` ends by setting `Finished(...)` and calling `refresh()`. `refresh()` enqueues a
continuation only when `hasNewUploadAlbums` is true — newly *discovered* albums, not "files are
waiting" — so a manual run of an album that already exists schedules nothing.

**The second row is the one with the long tail, and it is worse than one missing call.**
`markFirstBackupComplete()` has exactly one caller, `BackupWorker.kt:108` — and that line sits
*downstream of the hold check*. The worker evaluates the hold, and if the window is closed it returns
`Result.success()` at line ~80, before `engine.uploadPending()` and therefore before the completion
block ever runs.

So while the gate is up, **nothing is capable of noticing that the gate is no longer needed.** The
only code that lifts it is unreachable whenever it is holding.

**Confirmed on the Fold 4, 26 Aug 2026.** Haku finished — 19 of 19 uploaded and verified, nothing
pending in any upload-mode album. `files/datastore/` holds only `media_scope.preferences_pb`; no
`backup_settings.preferences_pb` exists, so `KEY_FIRST_BACKUP_DONE` was never written and
`hasCompletedFirstBackup` is still reading its default `false`. The backlog is clear and the gate is
still down.

It self-heals at the next window — at 1am the worker runs the engine, finds nothing outstanding, and
marks it — so the symptom is a gate held for up to fourteen hours after it stopped meaning anything,
reporting `first backup held (OUTSIDE_WINDOW)` when the honest answer is "there is nothing to do".
For a user who does their whole first backup through Sync now, that is the state they sit in.

**Both dead ends coincide during the first backup.** The path that chains is held by the window; the
path that runs does not chain. Which is why it sat at 4 of 19.

## Scale of the symptom

The byte budget caps a run at 512 MB. Against the 148 GB library on the Fold 8 that is ~290 presses
of Sync now — during exactly the period when automatic runs are gated and the button is the only
thing that moves. The control exists for "I have decided this is a good moment", and today it grants
that for 512 MB.

## The fix

**One host.** `runBackupNow` stops calling the engine directly and enqueues the same work the
scheduler already uses, so the chaining and the bookkeeping happen once, in one place. The existing
continuation logic then covers the manual case for free.

**A manual chain is not subject to the first-backup window.** Already the stated rule — *"Only
automatic runs are gated; Sync now is never held, because someone who asked has already decided this
is a good moment"* — but today it holds only for the first run of a manual chain, because every
continuation it schedules is an automatic one. The manual origin has to survive into the
continuations, or the manual path can never clear a backlog during the window.

**Stop cancels the chain**, not just the run in flight. Cancelling mid-upload is safe and cheap: the
resumable session URL is persisted on the row (verified on hardware 26 Aug), so a stopped file
resumes from its offset rather than restarting — provided the restart is prompt, since the session
expires about 15 minutes after the last chunk.

**The button carries both states.** `Sync now` when idle; `Stop sync` while a manual chain is live.
Today it reads `Syncing…` and is disabled, which is a label rather than a control.

## Do not lose the byte budget

It bounds a single *run*, which is what keeps memory, battery and a failed attempt small. The fix
makes many runs follow one another; it does not make one run unbounded.

## Where the manual chain lives — decided 26 Aug 2026: WorkManager

`viewModelScope` cannot host this. A run to completion over a real library is hours, and the scope
dies with the screen. **Ian chose the WorkManager chain**, no foreground service: it reuses
`enqueueContinuation`, survives backgrounding, needs no new permission and no Play listing change.

Three things decided it, in order of weight.

**1 — A foreground service could not finish the first backup inside its own budget.** Android 15+
caps `dataSync` foreground services at roughly six cumulative hours per 24, resetting when the user
foregrounds the app. Measured on the Fold 4 today: 499 MB in 107 seconds, about 4.7 MB/s. At that
rate the Fold 8's 148 GB is **~9 hours of transfer** — so the heaviest job the app will ever run is
the one that exceeds the cap, and would need two days or deliberate user interaction to complete.
*Worth re-checking against Android 17 docs before relying on the exact figure; this class of
restriction tightens release over release.*

**2 — The shade Stop button cannot be relied on anyway.** TASK-011 already records the rule: *"The
notification cannot be the only channel."* `POST_NOTIFICATIONS` is refusable, Android prompts once,
and a denial is silent. Anything reachable only from the shade is unreachable for those users. So an
in-app Stop has to exist regardless — which means building the WorkManager version either way, with
the foreground service adding a second optional surface rather than replacing anything.

**3 — WorkManager's own limit is already covered.** A JobScheduler execution gets roughly ten minutes.
A 512 MB batch took **110 seconds** on this connection, five times the headroom. On a slow link it
would not fit — 512 MB at 5 Mbps is about fourteen minutes — and that is exactly the case the
resumable session covers, verified working on hardware this morning: the run is killed, the next one
resumes from its offset, and WorkManager reschedules well inside the ~15-minute session window.

**Follow-on, not this fix:** the byte budget is tuned as a size and behaves as a time. 512 MB is two
minutes on fast wifi and past the job limit on a weak connection. A time-shaped budget would suit the
constraint better. Noted, deliberately out of scope here.

**Left open:** a foreground service with a progress notification remains a possible later addition
for shade-level visibility and a second Stop control. It is additive to this design, not a fork in
it. See TASK-011 for the `POST_NOTIFICATIONS` timing question it would depend on.

## Acceptance

- One press of Sync now clears the whole backlog, across as many byte-budget runs as that takes
- Stop is offered while a manual chain is live, and cancels the chain rather than one run
- A file stopped mid-upload resumes from its offset on the next run, not from byte zero
- A manual chain is never held by the first-backup window, in any of its continuations
- A backlog cleared by a manual chain lifts the first-backup gate, exactly as the worker path does
- The gate lifts whenever the backlog is clear, including on a run that is held — a closed window
  must never stop the app noticing there is nothing left to do
- A held run whose backlog is empty says so, rather than reporting that the first backup is waiting
- A manual chain survives the app being backgrounded, and continues rather than restarting if the
  process is killed mid-batch
- Stop is reachable in the app, never only from a notification
- The screen never reports `Finished` with files remaining and no reason given
- `markFirstBackupComplete` has no path that can be reached only by one of the two hosts
- Verified on hardware in both themes, per CLAUDE.md
